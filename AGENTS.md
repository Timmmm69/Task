# AGENTS.md — проект Task

## Область проекта
Работать только с продуктом Task: Windows desktop-органайзер для локальной сети компании.

## Канонические источники
1. `sources/concept/Task_Concept_Final.txt` — бизнес-требования.
2. `sources/stage_1/architecture_organizer.md` — архитектура Этапа 1.
3. `sources/stage_2_2/Organizer_Stage2_Technical_Specification_2.2.zip` — технический контракт.
4. `sources/stage_3_4/Organizer_Stage3_Final_Baseline_3.4.zip` — UX baseline.
5. `sources/stage_4_1_1/Organizer_Stage4_PRD_Candidate_4.1.1.zip` — кандидат PRD.

## Правила
- Не использовать файлы, память или решения из других проектов.
- Не читать соседние проектные папки без прямой команды.
- Не изменять содержимое `sources/`.
- Все рабочие изменения выполнять в `work/`.
- Все итоговые артефакты помещать в `outputs/`.
- Старые, сомнительные и конфликтующие файлы помещать в `archive/quarantine/`.
- При противоречии соблюдать порядок канонических источников выше.
- Не менять бизнес-требования без явного решения пользователя.
- Для каждого итогового пакета создавать manifest, версию, SHA-256 и validation report.
- Не объявлять этап завершённым без фактической проверки артефактов.

## Продолжение работы в новом чате
- Перед планированием или изменениями проверить состояние локальной копии (`git status`, текущую ветку и `origin/main`). Если локальный `main` отстаёт и рабочая копия чистая — синхронизировать её с `origin/main`; GitHub является источником общей актуальной истории, а локальная папка — рабочей копией.
- Прочитать `work/delegation/README.md` перед первой задачей, которую потенциально можно делегировать.
- Не требовать от пользователя отдельной просьбы о делегировании. Самостоятельно классифицировать независимые, decision-complete подзадачи:
  - **L / low:** до 3 файлов и 150 строк, без публичных интерфейсов, зависимостей, удалений или переименований.
  - **M / medium:** до 8 файлов и 400 строк, один изолированный модуль/сценарий с уже утверждёнными интерфейсами.
  - **H / high:** архитектура, API/DTO, БД/миграции, права/безопасность, синхронизация, deployment/backup/updates, неясные баги и большие рефакторинги — выполнять самостоятельно или сначала разбивать на L/M.
- Предпочитать содержательные, законченные L/M-инкременты: обычно 3–8 файлов и 150–400 строк. Не создавать искусственные микрозадачи; объединять мелкие правки одного сценария в один пакет.
- Когда есть подходящая L/M-задача, выдать пользователю один полный, готовый к копированию блок `DELEGATION_PACKET` на одну задачу и продолжить сквозную нумерацию чатов. Параллельные пакеты выдавать только при отсутствии пересечения файлов и семантических зависимостей. Не предлагать пользователю выбирать ветки, worktree, команды или вручную составлять prompt.
- Для обычного ручного чата DeepSeek пакет должен содержать все нужные требования, acceptance criteria, разрешённые и запрещённые файлы, reference files, публичный контракт при необходимости, тесты, stop conditions и процедуру публикации. Не отправлять в него весь PRD или историю обсуждений.
- Обычный ручной DeepSeek — основной режим: агент реализует production-код, проверяет его, коммитит и напрямую пушит L/M-задачу в `main`. Для medium Codex после push обязан проверить актуальный `origin/main`, diff и общий gate. В пакете для агента обязательно: `fetch`, чистое дерево, commit только scope-файлов, перед push `fetch` + `rebase origin/main`, повторная проверка; при конфликте или ошибке — ничего не пушить.
- Автоматический dispatcher `task-delegate` — отдельный опциональный PR-режим и используется только если пользователь явно выбрал его. Его `merge: automatic` / `merge: codex-review` относятся только к dispatcher и не отменяют правила ручного direct-push режима.
- В статусах для пользователя кратко объяснять: что уже в `main`, что проверено, что это даёт продукту и какой следующий шаг.

## Синхронизация dashboard
