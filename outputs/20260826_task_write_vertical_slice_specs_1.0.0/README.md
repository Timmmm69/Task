# Комплект технических заданий: Task write vertical slice 1.0.0

Комплект предназначен для последовательной передачи в шесть новых чатов. Каждый файл является самостоятельным промтом: его нужно передавать целиком, без пересказа и без добавления истории предыдущих обсуждений.

## Порядок выполнения

1. `01_SERVER_TRANSACTION_FOUNDATION.md` — транзакционная основа записи, durable idempotency, audit, domain events и outbox.
2. `02_SERVER_TASK_CREATE.md` — `POST /api/v1/tasks`.
3. `03_SERVER_TASK_PATCH.md` — `PATCH /api/v1/tasks/{id}`.
4. `04_SERVER_TASK_TRANSITION.md` — `POST /api/v1/tasks/{id}/transition`.
5. `05_DESKTOP_WRITE_API_CLIENT.md` — типизированный WPF-клиент записи.
6. `06_DESKTOP_WRITE_UX_AND_E2E.md` — формы создания и изменения, смена статуса, обработка конфликтов и реальный end-to-end gate.

Задания необходимо выполнять именно в этом порядке. Следующий чат разрешено запускать только после того, как предыдущий чат успешно отправил свой коммит в `origin/main`. Параллельный запуск запрещён: задания последовательно изменяют общий контракт записи и используют результаты предыдущих шагов.

## Исходная точка

- Базовый проверенный коммит на момент подготовки комплекта: `2b6a7685788c29e36a8b0ecec3bafc569c42d949`.
- Ветка: `main`.
- Перед каждым заданием исполнитель обязан получить актуальный `origin/main`; фиксированный базовый коммит выше является только контрольной исходной точкой, а не основанием игнорировать более новые принятые коммиты.
- В текущем baseline уже существуют: PostgreSQL persistence для задач, доменный `TaskAggregate`, optimistic concurrency в `TaskLifecycleService`, защищённые read-only endpoints, production WPF shell и экран задач.

## Граница вертикального среза

Этот комплект реализует запись только для уже поддерживаемой production-моделью части задачи: заголовок, приоритет, начало, срок и статус. Он не должен притворяться полной реализацией всей Stage 2.2 схемы `TaskCreate`/`TaskPatch`. Поля project, parent task, description, requester, counterparties, assignees, watchers, recurrence и planned local schedule остаются отдельными будущими increments. Неподдерживаемые входные поля нельзя молча игнорировать.

## Итог комплекта

После шестого задания пользователь должен иметь проверенный сценарий:

1. авторизованный пользователь с правом записи создаёт задачу в WPF;
2. задача сохраняется в реальном PostgreSQL и сразу появляется в списке;
3. пользователь изменяет заголовок, приоритет и расписание с `If-Match`;
4. пользователь выполняет допустимую смену статуса;
5. повтор запроса с тем же `Idempotency-Key` возвращает сохранённый ответ без повторного изменения;
6. устаревшая версия не перезаписывается и отображается как понятный конфликт;
7. бизнес-изменение, audit, domain event, outbox и завершённая idempotency response фиксируются одной транзакцией;
8. итог подтверждён тестами, реальным PostgreSQL + HTTPS API + WPF end-to-end прогоном и версионированным validation package.
