# OPS-03 — backup and recovery, version 0.6.0

The production `Task.BackupAgent` now schedules and supervises real PostgreSQL backups. The Linux operator image in `deployment/backup` includes PostgreSQL 16, pgBackRest and the fixed operation runner. The Windows desktop remains unchanged. The thin .NET image in `deployment/containers` supports explicitly disabled hosting for packaging tests; it does not contain the Linux backup tools. Use the operator image for actual protection.

## Contract and operating policy

Sources: architecture stage 1 sections 15.15 and 16; stage 2.2 `03_runtime_operations_and_testing.md` background job catalog. Daily full copies at 01:00 UTC by default, continuous synchronous WAL archiving to **both** repositories with `archive_timeout=60s`, archive receipt checks every five minutes, weekly PITR verification. A cold start with no successful backup runs immediately. Every full copy is restored and its database pages/indexes checked before retention is allowed. Configuration/recovery-input changes detected by the five-minute check trigger a new full backup. During planned configuration changes, run `backup` explicitly after publishing a stable recovery-input snapshot.

The first repository retains a 30-day recovery window (minimum 14); the second retains 366 days (minimum 366). These are time windows, not counts: pgBackRest also preserves the base required to cover the window. Daily full copies on the secondary conservatively cover the architecture's weekly/monthly examples without a separate GFS deletion algorithm. Provision capacity for **all daily full sets and WAL** in this window. WAL expiration remains coupled to retained base backups; never delete WAL files manually. Automatic pgBackRest expiry is disabled. The agent calls expiry only after successful physical restore from both newly completed copies. An off-host failure therefore preserves the previous recovery sets.

No application API can submit arbitrary commands or overwrite the production database. Operator commands are `backup`, `check`, `verify`, `health`, `plan`, `restore`. Administrative API/UX actions remain part of the separate administration backlog. Restore always allocates a new directory below `/restore`, maps tablespaces there and starts PostgreSQL with no TCP listener and archive writes disabled. It never offers a production destination or automatic cutover.

## Provisioning

1. Build `docker build -f work/production/deployment/backup/Dockerfile -t task-backup-ops:0.6.0 work/production`. Run the verification gate below, record the resulting image ID/digest and package inventory, then pin `TASK_BACKUP_IMAGE` to the tested immutable image. .NET bases and NuGet locks are pinned. Ubuntu packages are resolved from signed repositories at build time; this additional operator image does **not** inherit the independent reproducibility claim of release 0.5.0. Revalidate it when rebuilding.
2. Use a Linux server/VM or supported Linux container host with PostgreSQL 16. Prepare `TASK_PGDATA`, a separate disk for `TASK_LOCAL_BACKUP`, and an NFS/SMB mount from another host for `TASK_OFFHOST_BACKUP`. The runtime verifies the remote filesystem type and rejects a local-only secondary. The local repository must reside on a different filesystem from PGDATA. Both repositories need backup-operator access. UID/GID is **1001:1001**; directories should be mode 0700. A different filesystem alone cannot prove physical disk separation: verify device placement during deployment.
3. Configure immutable NAS snapshots/offline copies under a separate storage administrator. The agent needs write access to its live repository; it cannot itself make that repository ransomware-immutable. Verify retention and a restore from the independently protected snapshot during quarterly disaster drills. Do not put the snapshot administration credentials in this container.
4. Prepare `TASK_RECOVERY_KEYS`, mode 0700, with `repo1-key`, `repo2-key`, `assets-key`: three **different**, cryptographically random 32-byte values encoded as 64 hex characters. Files are mode 0400 and readable by UID 1001. Add `postgres-password` only for initializing a new database. Generate keys with the corporate secret manager or `openssl rand -hex 32`; never commit them or put them in Compose environment variables. Keep two controlled escrow copies on separate media, outside this server. The agent reads keys from read-only secret files. Generated pgBackRest configuration lives in a private tmpfs.
5. Prepare `TASK_RECOVERY_INPUT` as a stable, read-only snapshot with nonempty directories: `configuration`, `keys`, `certificates`, `assets`, `installers`, `migrations`. Include server configuration/templates, actual recovery material or resolvable escrow references, CA/server certificates and rotation metadata, avatars/system assets, signed installers/update manifests and exact migration binaries/scripts. If a category is not deployed, place an explicit `not-applicable.json` with its reason. Do not include live access tokens, client caches or temporary files. Symlinks and special files are rejected. Each capture has an encrypted SHA-256 manifest; the tar bundle is AES-256-GCM authenticated, with a fresh nonce. Database and WAL repositories use pgBackRest AES-256-CBC and pgBackRest integrity checks.
6. Set the required `TASK_*` paths and use `docker compose -f work/production/deployment/backup/compose.yaml up -d`. It exposes no database host port. The agent has no network interface and uses a shared Unix socket; it mounts production PGDATA read-only. The dedicated `task_backup` DB role has monitor/checkpoint/physical-backup function grants, not superuser or migration rights. On an **existing** cluster, have its DBA review/apply `initialize.sql`, the peer identity mapping in `entrypoint.py`, and the WAL configuration before enabling the agent. The entrypoint does not retrofit an existing cluster or apply product migrations. Product migrations still use Task.DatabaseMigrator.
7. Set `TASK_BACKUP_HOUR_UTC` if the local maintenance window differs (01:00 Minsk = 22:00 UTC on the preceding date). `TASK_BACKUP_VALIDATION=1` is solely for disposable test fixtures; never set it in deployment.

## Status, failures and maintenance

`docker compose -f work/production/deployment/backup/compose.yaml exec backup-agent /opt/task-backup/runner.py health` returns exit 0 only when the last base backup is at most 26 hours old, the last archive check at most 10 minutes old, and the last PITR drill at most 8 days old, with no failed operation. Compose reports unhealthy otherwise. Route unhealthy status and critical .NET logs to the operations owner's alert system (OPS-04); also alert on DB/WAL/repository/free restore-work capacity. PostgreSQL archive failures do not silently discard WAL; an extended outage can fill its disk and requires intervention.

Persistent `/var/lib/task-backup/status.json` holds scheduler timestamps, and `journal/*.json` holds each direct runner outcome without secrets. OS-held locks serialize agent instances and runner commands. Failure retains prior success timestamps and retries after five minutes. Timeouts/cancellation kill the child process tree. Invalid scheduler JSON is preserved under `invalid-status-*` and triggers a new copy. A backend failure never becomes a success merely because a file exists. Investigate protected storage and PostgreSQL/pgBackRest diagnostics using the operator account; application logs intentionally omit child output.

The journal is small but append-only; archive it according to the company's audit policy. `/restore` needs room for a complete cluster, tablespaces and recovery assets. Successful automated drills are removed. Interrupted process/container termination can leave a `drill-*` directory; inspect it with `pg_ctl status` before operator cleanup. Never clean PGDATA or repository paths to free restore space.

For key rotation, create a **new repository/path** with the new key and verify its first backup and restore. Preserve the old repository and escrow keys until its retention expires. Do not change a cipher key in place. For `assets-key`, retain the matching operator configuration/image and old key for old envelopes; verify both generations before retiring either. The envelope format is versioned (`TASKRECOVERY1`); it never contains the decryption key.

## Point-in-time incident recovery

1. Declare the incident, block writes at the application/service edge and record the desired UTC recovery time, selected backup label, software version and expected loss window. Preserve evidence. Production cutover requires the incident owner's two-person approval under the technical contract; this tool only prepares an isolated recovery.
2. On a compatible isolated host, use the tested image and escrow keys, mount the selected repository (default secondary), a fresh `/restore` volume and persistent operator state. A recovery operation needs neither the original PGDATA nor recovery-input snapshot nor the unselected repository's storage. Supply all three escrow key files to generate the configuration. The bundle is retrieved from the selected repository itself. For read-only repository restore, start the persistent `recovery-operator` service (profile `recovery`), or run the image with command `operator` and only the selected repository mounted. Use `docker exec` to invoke `/opt/task-backup/runner.py plan` and `restore` inside it. Keep this operator container running while examining the restored database. It has no production database/socket mounts and its repositories are read-only.
3. Inspect `pgbackrest --config=/run/task-backup/pgbackrest.conf --stanza=task --repo=2 --output=json info` in the operator container. Select a full backup completed **before** the target time. `plan --repo 2 --label <label> --target <ISO-UTC-time>` validates this choice without writing database data. A future, timezone-less or pre-backup target is rejected.
4. Execute `restore --repo 2 --label <label> --target <same-ISO-UTC-time>`. The result gives a unique data directory and Unix socket. The command requires successful recovery to the requested target, authenticated asset verification, and `pg_amcheck`. A failed target or integrity check fails the operation and removes the failed plaintext workspace. No production paths are replaced. Successful operator restores remain running for examination.
5. Connect via the returned Unix socket as `postgres`; check expected rows, migration version, task/calendar/audit data and business consistency. The successful restore result includes `assets.archive`, an already authenticated and manifest-verified tar in the private recovery directory. Inspect it and deploy only the approved configuration/key/certificate files; treat its plaintext as recovery secrets and remove it with the incident workspace after use. Run the exact matching API image in restricted mode and smoke-test login, task query, audit and catalog metadata. Reconcile SMB/NAS metadata separately; this system does not back up employees' physical files.
6. Record the measured duration, recovered target and actual data-loss window. After the two-person cutover decision, follow the company DNS/service endpoint procedure and client sync-reset procedure. Stop the isolated instance with `pg_ctl -D <returned-data-directory> -m fast -w stop`. Keep incident evidence; clean only the named isolated directory after approval under incident policy.

## Verification

Run from the repository root with PowerShell 7 and Docker Linux:

The existing `production-package` CI job runs this gate after container packaging succeeds, through `Test-ContainerPackaging.ps1`. Failures stop the job; the normal thin BackupAgent host lifecycle check alone does not satisfy this gate.

```powershell
pwsh -NoProfile -File work/production/verification/Test-BackupRestore.ps1
dotnet test work/production/tests/Task.ServiceHosts.Tests/Task.ServiceHosts.Tests.csproj --no-restore --filter 'FullyQualifiedName~Backup'
```

The integration gate provisions a unique networkless disposable PostgreSQL cluster, applies all current product SQL migrations, backs up both encrypted repositories, restores before a destructive delete, verifies post-base commits/schema and unchanged primary state, exercises actual WAL drills, corrupt copies, invalid keys, off-host failure, retention guardrails and the real hosted agent. It removes only its named fixture containers/volumes and its bounded `work/tmp` directory. Test secrets never enter the result package.

The local gate proves software behavior. The final incident test starts with fresh operator state and restore volumes, the original server stopped, and only a read-only secondary repository plus escrow keys. Successful backup journal entries include database/repository bytes and completion time alongside the restore duration. `run.json` binds a successful, cleaned-up run to SHA-256 hashes of the tested backup sources; packaging refuses a failed run or changed source files. Linux executable scripts retain LF line endings on Windows checkouts.

It cannot attest the company's physical off-host disk placement, immutable snapshots, key escrow access, production-sized RTO ≤4h, or alert delivery. Complete and record those deployment checks on the actual company infrastructure before declaring production data protected.
