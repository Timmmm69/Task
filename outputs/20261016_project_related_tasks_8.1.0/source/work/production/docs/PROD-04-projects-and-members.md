# PROD-04 — проекты и участники

Версия реализации: 1.0.0.

## Результат

Раздел «Проекты» в production Windows-клиенте больше не является заглушкой. После входа он
загружает только разрешённые сервером проекты и показывает карточку выбранного проекта, статус,
сроки, владельца, руководителя, активных участников с проектными ролями и связанные задачи.

Пользователь с соответствующими capabilities может создать или изменить проект, перевести его в
один из контрактных статусов, архивировать завершённый проект, добавить участника, изменить его
роль или удалить участника. Владелец не удаляется через операцию участника: сервер требует сначала
выполнить отдельную передачу владения.

## Контракт и безопасность

- Все чтения и команды выполняются через authenticated executor; `401` проходит существующий
  single-refresh flow, а terminal auth failure переводит поверхность в безопасное состояние.
- UI использует capabilities только для presentation. Каждый endpoint сохраняет серверную policy и
  object/project-scope проверку.
- Записи не применяют optimistic state: UI меняется только после authoritative response.
- Изменения передают strong `If-Match`; create/add/change/archive используют idempotency key.
- `403`, `404`, `412`, validation/state conflicts и transport failure отображаются как ограниченные
  безопасные состояния без раскрытия серверных деталей.
- Новый канонический `GET /api/v1/project-roles` доступен по `Project.Read`. Он возвращает только
  активные роли с project permissions; административные и не назначаемые обычным руководителем
  роли отфильтрованы сервером.

## Связанные задачи

Клиент использует существующий типизированный Task API и оставляет только задачи, чья карточка
содержит выбранный `projectId`. Основные сведения и участники загружаются независимо от задач.
Сохранённое раскрытие секции `projects/v1/tasks` не запускает запросы: пользователь нажимает
«Загрузить задачи», затем «Продолжить поиск», по одной cursor-странице за нажатие. Найденные задачи
появляются после каждой страницы, без повторов по Id. До конца pagination UI явно показывает
частичный результат, в том числе при нуле совпадений. Пустота подтверждается только концом обхода.

Ошибку страницы можно повторить с тем же cursor; ошибочный/повторяющийся cursor требует явного
начала поиска заново. Произвольного ограничения числа страниц нет. Сворачивание, выгрузка экрана,
деактивация, смена проекта и потеря доступа отменяют запрос; поздние ответы проверяются по поколению
и контексту. `403`/`404`, отзыв чтения и завершение сессии очищают задачи. При transport failure или
offline ранее подтверждённый частичный результат остаётся для просмотра в текущей сессии.
Без `Task.Read` запросы задач не выполняются, UI сообщает об отсутствии права отдельно от пустоты.

API, DTO, permissions и серверная видимость сохранены. Для полного списка по-прежнему нужен обход
всех доступных задач: ускорение серверной выборки по проекту не заявляется. Воспроизводимые проверки
Этапа 8.1 и сравнение с исходным поведением находятся в
`outputs/20261016_project_related_tasks_8.1.0/validation-report.md`.

## UX-границы

Этап 5.2 подключает общий Employee Picker 5.1 в добавление участника и выбор необязательного
руководителя. При `User.Read` поиск показывает имя и login; запись передаёт подтверждённый
UserAccountId через существующие DTO. Перед отправкой активность проверяется повторно, а сервер
сохраняет окончательную проверку tenant/status. Имена владельца, руководителя и участников
разрешаются через существующий `GET /users/{id}` только при `User.Read`; недоступные имена
показываются нейтрально. Кэша между формами, аккаунтами или организациями нет.

`Project.ManageMembers` по-прежнему не гарантирует `User.Read`. Для такой роли сохранён UUID-ввод
участника и руководителя, без запросов к User API. Полный отказ от UUID для всех ролей блокируется
контрактом прав и требует отдельного решения; автоматических grants и обходных endpoints нет.
Подробности, матрица доступа и ограничения: `PROJECT-EMPLOYEE-PICKER-5.2.md`.

## Проверка

Автоматизированы строгий mapping project API, canonical URI и headers, controlled failures,
capability gating, загрузка ролей/участников/связанных задач, создание и изменение версии после
membership command. Route-policy suite проверяет deny-before-store для всех product endpoints,
включая `GET /api/v1/project-roles`.

PostgreSQL runtime не изменялся миграцией: endpoint читает уже существующие `iam.roles` и
`iam.role_permissions`. На машине сборки Docker/PostgreSQL недоступны; это честно отражено в
validation report. Ранее подтверждённый API-04 PostgreSQL gate остаётся базой для существующих
project/member write paths.
