# SEC-02 — роли и доступ к объектам

Версия реализации: 1.0.0. Версия схемы: 13.

Основание: `sources/concept/Task_Concept_Final.txt`, раздел 7; `sources/stage_1/architecture_organizer.md`, раздел 10; технический контракт 2.2, `catalogs/permissions.csv` и `PUT /api/v1/users/{id}/roles`. Исходные документы не изменены.

## Системные роли

| Роль | Возможности | Граница данных |
|---|---|---|
| system_administrator | Управление пользователями, назначение ролей, администрирование; существующий offline bootstrap выдаёт явные permissions | Организация; явный deny проверяется до административного доступа |
| system_manager | Создание и управление проектами, задачи и назначения, контакты, взаимодействия и каталог | Свои объекты и проекты с разрешающим членством/ролью |
| system_employee | Создание задач, изменение статуса собственных/назначенных задач, комментарии, доступные контакты и ссылки | Свои/назначенные объекты и доступные проекты; нет управления ролями и чужими задачами |
| system_observer | Чтение доступных проектов, задач, файлов и комментариев | Только доступные объекты; нет бизнес-команд записи |

Личные настройки, собственные уведомления и сессии доступны независимо от отсутствия бизнес-команд записи. Роль не назначается автоматически при миграции: новые пользователи остаются без доступа до явного назначения администратором. Три бизнес-шаблона создаются для существующих и новых организаций. Их permissions перечислены явно в миграции; новые permissions не попадают в бизнес-роли автоматически. Администратор создаётся существующим offline bootstrap.

## Принятие решения

1. Аутентификация проверяет действующую учётную запись, сессию и организацию.
2. Endpoint требует capability; отсутствие, неактивная permission и explicit deny закрывают доступ.
3. SQL ограничивает выборку до пагинации: организация, отношения с объектом, активное членство и проектные запреты.
4. Команда повторно проверяет права на объект в транзакции. Product API и task commands перечитывают capabilities после общего блокирования транзакций организации. Назначения и watchers требуют отдельных прав.
5. Проверки выполняются и перед выдачей сохранённого idempotency-ответа. Search snapshot повторно проверяет видимость.

Приватные задачи без проекта больше не считаются общими. Создание повторяющихся задач переносит в карточку исполнителей, наблюдателей и проект; миграция заполняет эти атрибуты у нетронутых старых occurrences. Контакты, компании, взаимодействия и каталог доступны создателю либо через направленные доменные связи с доступным проектом/задачей. Каталог наследует область родительской папки, взаимодействие — контрагента. Произвольная связь `related` не раздаёт доступ. Создание связи, расширяющей доступ к целевому объекту, требует права изменения его области. Открытие пути дополнительно сохраняет ограничения устройства и Windows/SMB ACL.

Единые правила применены к спискам, карточкам, каталожному дереву, истории, поиску и search snapshots, подбору объектов для задачи, файлам задачи, archive/trash, file locations и уведомлениям об объектах. Календарь и конфликты используют actor-aware SQL; событие проверяется при чтении и записи. Серии повторений и occurrences также ограничены пользователем. Внутренние unscoped методы хранилищ остаются для мигратора/фоновых задач/тестовых fixtures; HTTP-адаптеры используют scoped-варианты.

## Назначение и отзыв

`GET /api/v1/roles` требует `Role.Read`. `PUT /api/v1/users/{id}/roles` требует одновременно `User.ManageRoles` и действующее `organization.manage`, принимает канонические `roles` и `expectedUserVersion`, требует `If-Match` и `Idempotency-Key`.

Назначение атомарно меняет набор ролей и версию пользователя, увеличивает authorization scope version, создаёт audit/domain event/outbox. Запрещены роли другой организации, дубли, устаревшая версия и удаление последнего активного администратора. Блокировка/деактивация последнего администратора также запрещена и использует тот же transaction lock. Миграция увеличивает существующие scope versions, чтобы клиенты не продолжали использовать старую область кэша.

Поддерживаются организационные назначения, проектные роли/overrides, `departmentId` и `validUntil`. Отдел должен быть активным объектом той же организации. Department scope пересекается с существующими отношениями: сам по себе отдел не открывает все объекты. Для проекта используется отдел владельца, для задачи в проекте — отдел владельца проекта, для личного объекта — отдел создателя; связанный каталог/контакт может использовать область доступного родительского проекта. Scoped deny проверяется для соответствующей области до allow. Истёкшие назначения исключаются при каждом вычислении capabilities и object scope. Административные permissions допускаются только в постоянной организационной роли, чтобы истечение срока не лишило компанию последнего администратора.

Административное чтение Product API, задач, календаря и повторений журналируется как `authorization.administrative_read`, без содержимого объектов и путей. Запись использует существующие доменные audit events.

## Проверка и развёртывание

`powershell -ExecutionPolicy Bypass -File work/production/verification/Test-Authorization.ps1` создаёт отдельный PostgreSQL 16 на localhost с временным ASCII-каталогом, выполняет все три тестовых проекта и сохраняет TRX в `work/production/evidence/sec02`. Рабочая БД не используется. Дополнительно выполняются `Test-SecurityGate.ps1 -NoBuild`, `Test-ProjectBoundaries.ps1`, dashboard validation и `git diff --check`.

Перед обновлением нужен обычный проверенный backup. Применить миграцию 13 через штатный migrator и повторно применить `deployment/containers/sql/grant-runtime.sql`: runtime получает DELETE только на `iam.user_roles`, необходимый для атомарной замены назначений. Коллизия зарезервированного кода с пользовательской ролью останавливает миграцию; пользовательская роль не перезаписывается. Физические SMB ACL и TLS/secrets относятся к соответствующим отдельным задачам.
