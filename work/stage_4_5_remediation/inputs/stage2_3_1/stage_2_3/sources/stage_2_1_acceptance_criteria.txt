Переходим от аудита к исправлению.

Твоя задача — выполнить полный Этап 2.1: устранить все выявленные инженерные дефекты, привести документацию и исполняемые артефакты к единому непротиворечивому состоянию и доказать их работоспособность автоматическими проверками.

Работай с теми же файлами, на основании которых был проведён аудит.

Твой предыдущий аудит является обязательным входным документом. Нельзя пропускать замечания, снижать их серьёзность без доказательства или объявлять проблему исправленной только на основании изменения документации.

# Главная цель

После завершения работы должны одновременно выполняться следующие условия:

1. Все Critical устранены.
2. Все блокирующие High устранены.
3. PostgreSQL DDL реально исполняется на чистой PostgreSQL 16.
4. Все миграции применяются последовательно.
5. Authorization seed создаёт точную каноническую модель прав.
6. OpenAPI 3.1 является полноценным машиночитаемым контрактом.
7. Optimistic locking и idempotency присутствуют непосредственно в HTTP-контрактах.
8. Схема БД, API, события, permissions и документация не противоречат друг другу.
9. Автоматические проверки подтверждают результат.
10. После повторного независимого аудита можно объективно решить, допустим ли переход к реализации.

# Правила работы

Не ограничивайся рекомендациями.

Не составляй только план исправлений.

Не переписывай весь комплект с нуля без необходимости.

Исправляй существующие файлы точечно, сохраняя согласованные решения Этапа 1 и непротиворечивые части Этапа 2.

Для каждого дефекта:

* найди все связанные артефакты;
* определи каноническое решение;
* внеси изменения во все затронутые документы и файлы;
* добавь проверку, которая не позволит дефекту появиться повторно;
* зафиксируй трассировку «дефект → решение → изменённые файлы → проверка».

Не объявляй проблему устранённой, если исправлен только один из противоречащих файлов.

# Приоритет выполнения

## Волна 1. Исполняемость базы данных

Исправь CR-01 и все связанные SQL-проблемы.

Нужно:

* исправить синтаксис DDL;
* развернуть чистую PostgreSQL 16;
* применить миграции в правильной последовательности;
* проверить constraints, foreign keys, triggers, indexes и seed;
* проверить повторное применение там, где требуется идемпотентность;
* сохранить полный лог выполнения;
* добавить автоматическую проверку чистого развёртывания.

Если в текущей среде невозможно запустить PostgreSQL 16, подготовь Docker Compose или другой воспроизводимый локальный способ запуска и выполни проверку через него.

Недостаточно проверить SQL статическим анализатором.

## Волна 2. Каноническая модель авторизации

Исправь CR-08, CR-09 и связанные проблемы.

Нужно:

* определить точный канонический список permission-кодов;
* оставить ровно согласованное количество разрешений;
* удалить устаревшие и некорректные permission-коды;
* создать системные роли;
* создать проектные роли;
* создать полную role-permission matrix;
* определить bootstrap первого администратора;
* устранить использование read permissions для write-операций;
* проверить все 240 API-операций на существование permission-кода;
* проверить отсутствие permission-кодов, которые не используются и не предусмотрены моделью;
* запретить восстановление объекта без соответствующего доменного Restore/Unarchive permission.

Создай автоматические тесты согласованности:

API → permission catalog → seed → role mappings.

## Волна 3. Полноценный OpenAPI-контракт

Исправь CR-02, CR-03, CR-04 и связанные High-дефекты.

Нужно:

* заменить используемые универсальные object-схемы на конкретные DTO;
* определить required fields;
* определить enum;
* определить ограничения строк, чисел, коллекций и форматов;
* запретить неизвестные поля в command DTO там, где это необходимо;
* определить конкретные response DTO;
* определить page DTO;
* определить query parameters;
* определить стабильные error codes для операций;
* добавить If-Match;
* добавить Idempotency-Key;
* добавить ответы 409, 412 и 428 в соответствии с выбранной семантикой;
* исправить `/auth/refresh`;
* согласовать Project status между OpenAPI, state machine и PostgreSQL;
* решить команды, которым требуется проверка нескольких версий;
* проверить, что generated clients получают типизированные модели.

Запусти:

* OpenAPI validation;
* lint;
* generation минимум одного server stub;
* generation desktop/client SDK;
* компиляцию сгенерированных артефактов либо максимально близкую доступную проверку;
* contract tests для критических операций.

## Волна 4. Durable idempotency

Исправь CR-05.

Спроектируй и реализуй в DDL:

* таблицу idempotency records;
* caller scope;
* endpoint/operation scope;
* idempotency key;
* request hash;
* статус выполнения;
* HTTP status результата;
* сохранённый response либо безопасную ссылку на результат;
* время создания;
* expiry;
* обработку параллельного claim;
* повтор с тем же body;
* повтор с другим body;
* crash до commit;
* crash после business commit, но до ответа.

Согласуй:

* DDL;
* middleware;
* API;
* транзакционные границы;
* очистку записей;
* тесты.

## Волна 5. Lifecycle, корзина и purge

Исправь CR-06, H-06 и связанные дефекты.

Для каждого типа сущности однозначно определи:

* является ли она `core.object`;
* имеет ли собственный lifecycle;
* поддерживает ли архив;
* поддерживает ли корзину;
* поддерживает ли восстановление;
* допускает ли physical purge;
* что происходит с дочерними объектами;
* какая permission требуется.

Особенно проверь:

* Role;
* Checklist;
* RecurrenceSeries;
* Reminder;
* Comment;
* Project;
* Task и subtasks;
* File Catalog folders и descendants.

Приведи в соответствие:

* DDL;
* foreign keys;
* API;
* события;
* permissions;
* фоновые процессы;
* документацию;
* sequence diagrams.

## Волна 7. Конкурентность и графовые инварианты

Исправь H-03 и H-04.

Нужно:

* определить aggregate version для каждой команды;
* либо использовать typed expected-version fields;
* определить версии member/project, series/task и location/item;
* проверить reparent задачи с существующими descendants;
* запретить глубину иерархии сверх разрешённой;
* исключить циклы зависимостей;
* исключить циклы файлового каталога;
* определить lock ordering;
* применить advisory locks или SERIALIZABLE там, где это необходимо;
* определить retry policy;
* создать конкурентные тесты.

## Волна 8. Tenant boundary

Исправь H-05.

Даже если MVP работает в одной компании, схема должна физически исключать недопустимые cross-organization relations.

Для security-relevant связей примени:

* composite unique constraints и foreign keys `(organization_id, id)`;

либо:

* проверяемые constraint triggers, если composite FK технически нецелесообразны.

Проверь:

* project owners;
* project members;
* task actors;
* assignees;
* observers;
* contacts;
* attendees;
* file references;
* roles;
* devices;
* notifications.

Добавь negative database tests.

## Волна 9. Audit и history

Исправь H-07.

Нужно:

* обеспечить insert-only модель на уровне PostgreSQL;
* разделить migration owner и runtime role;
* запретить UPDATE/DELETE runtime-роли;
* обеспечить уникальность истории версии объекта;
* определить retained tombstone;
* согласовать history с physical purge;
* исключить запись секретов и чувствительных данных;
* добавить тесты неизменяемости.

## Волна 10. Change feed и bootstrap synchronization

Исправь H-08 и H-10.

Выбери единственный канонический механизм формирования change feed:

* запись в business transaction;

либо:

* idempotent projection из transactional outbox.

Не сохраняй оба конкурирующих механизма.

Нужно определить:

* source domain event ID;
* dedupe;
* sequence;
* порядок;
* cursor;
* snapshot cut;
* bootstrap session;
* typed datasets;
* pagination;
* изменения во время snapshot;
* обязательный catch-up после snapshot;
* повторное подключение;
* потерю страницы;
* очистку локального cache;
* тесты записи во время bootstrap.

Для фоновых процессов добавь:

## Волна 12. Файловая модель и безопасность путей

Исправь H-11, M-05, M-06 и связанные проблемы.

Нужно:

* получать device ID и user ID из текущей session, а не доверять body/query;
* определить owner файла и пути;
* определить visibility точного path;
* запретить просмотр локального пути другого пользователя без специального разрешения;
* принимать probe telemetry только от текущего session-device;
* привязать UNC к разрешённому активному network resource;
* проверять canonical containment;
* исключить path injection;
* хранить availability в device-specific projection;
* не позволять одному устройству глобально объявлять путь недоступным для остальных.

## Волна 13. Reminder state machine

Исправь H-12.

Выбери единый набор состояний и терминов.

Согласуй:

* fired;
* delivered;
* snoozed;
* dismissed;
* cancelled;
* failed.

Добавь строгие CHECK constraints:

* `before_*` требует offset;
* `at_*` не принимает бессмысленный offset;
* dismiss и cancel имеют различную семантику;
* snooze создаёт корректное следующее occurrence.

## Волна 14. Канонический источник концепции

Исправь H-13.

Нужно:

* определить, какая версия концепции является канонической;
* вычислить hash каждого входного документа;
* провести semantic diff;
* перечислить различия;
* заново выполнить traceability validation;
* обновить validation report;
* не объявлять соответствие требованиям, пока hash и версия источника не совпадают.

# Реестр исправлений

Создай таблицу:

| Audit ID | Severity | Root cause | Decision | Changed files | Tests | Status | Residual risk |

В таблице должны находиться все:

* CR-01–CR-09;

Статус `Fixed` допустим только при наличии автоматической либо исполняемой проверки.

Если исправление не выполнено, используй `Open` или `Partially fixed`.
