# Этап 13.2 — файлы проекта

Версия: 13.2.0. Дата: 2026-10-19. Ветка: feature/project-detail-sections.
База: 283bcd4 (реализованный и проверенный этап 13.1 поверх origin/main dcbaca2).
Изменение относится к категории H: permissions, версии и асинхронный контекст; реализовано Codex самостоятельно.

## Реализация

ProjectFilesViewModel владеет подтверждённым снимком исходящих project_file выбранного проекта. Подключение через необязательный параметр ProjectsViewModel сохраняет существующие сценарии и тестовые hosts без файлового клиента. CorporateApplicationContext передаёт существующий DesktopWorkApiClient. Раздел загружается при раскрытии; подтверждение обзора проекта обязательно. Переход A→B отменяет старый контекст; поздние ответы не применяются. Раскрытый раздел повторно загружается для нового проекта после завершения старой команды. Collapse/unload/deactivate, смена организации/прав, logout и offline очищают снимок и отменяют операции. Данные файлов не сохраняются на диск.

Используется существующая реализация Object Link Target Picker: поиск доступного catalog_item по имени, подтверждение выбора, затем отдельное подтверждение привязки. UUID вручную не вводится. Тип связи фиксирован project_file. Перед POST проверяются полученные через каталог ID, тип и active lifecycle цели; сервер дополнительно проверяет object-level FileCatalog.Update и права на проект. Повторное создание одинаковой связи блокируется по подтверждённому снимку; конкурентный дубликат обрабатывается по ответу сервера. Самоссылка и неподходящий тип не отправляются.

Удаление принимает только выбранный экземпляр строки из текущего снимка, с исходным проектом и project_file. DELETE использует ID связи, а не ID объекта каталога. Никаких операций удаления/перемещения физического файла или объекта каталога нет. После успешной записи существующий клиент выполняет read-back; только после него и получения метаданных применяется новый снимок. При неясном результате, конфликте или ошибке запись блокируется до обновления. Подтверждённая версия обновляет карточку без потери имён сотрудников; версия открытого editor draft не перебазируется, чтобы сохранить обнаружение конфликта.

Названия и типы получаются отдельными разрешёнными GET catalog-items/{id}; поле названия в Object Links API не предполагается. При 403/404/trashed/ошибке метаданных отображается нейтральная строка, открытие/навигация отключены. Частичный доступ и ошибка получения связей отличаются от успешного пустого результата. Все страницы связей загружает существующий DesktopObjectLinks client; частичный набор страниц не подтверждается.

Переход в каталог использует существующий маршрут shell OpenWorkObjectAsync. Перед переходом или открытием цель повторно читается. Путь запрашивается только по явной команде открытия, при FileReference.Open, через resolve-location. Необходимы CanOpenOnDevice, включённое расположение и непустой RawPath; затем WindowsFileAccessAdapter проверяет реальную доступность/допустимость пути. Путь из сохранённых метаданных не считается доказательством доступности. Пути не показываются в UI; AutomationProperties.Name строки содержит только название и тип, без record.ToString и дополнительных полей DTO.

## API и permissions

- GET /api/v1/projects/{id}: Project.Read, подтверждение конкретного проекта/организации.
- GET /api/v1/objects/{id}/links: ObjectLink.Read + применимые права и object/project visibility; существующий cursor/limit/ETag контракт.
- GET /api/v1/catalog-items/{id}: FileCatalog.Read + серверная область доступа, без запроса расположений.
- GET /api/v1/object-link-targets: ObjectLink.Create + чтение допустимых типов; существующий picker, без fallback на общий каталог.
- POST /api/v1/objects/{id}/links: ObjectLink.Create, Project.Update, object/project checks и проверка FileCatalog.Update на цели. Body sourceObjectId/targetObjectId/linkType=project_file неизменён.
- DELETE /api/v1/objects/{id}/links/{childId}: ObjectLink.Delete и Project.Update с object/project checks. childId — ID связи.
- POST /api/v1/catalog-items/{id}/resolve-location: FileReference.Open и серверные проверки каталога/пользователя/устройства/ресурса.

Глобальные capabilities используются для предварительного отключения действий; разрешение на конкретный объект окончательно устанавливает сервер. Проверки сервера изучены в PostgresProductApiLinks.cs, CheckLinkWrite/CheckObjectAction/CheckProjectWrite. ETag/If-Match, idempotency/correlation и обработка ошибок остаются существующими. Новые permissions, API, DTO сервера, БД и зависимости не добавлены.

## Проверка и ограничения

Итоги и история запусков: validation-report.md. Полный desktop 1680 PASS; профильный набор 293 PASS; endpoint picker 1 PASS. Реальная WPF-проверка: раскрытие, фокус/traversal, названия/типы, общий picker, права открытия, collapse/reload; PNG сохранены и визуально проверены. Транспортная проверка проходит 201 project_file через две страницы и отдельные разрешённые GET имён; существующие регрессии клиента покрывают 451 связь, смену версии/повтор курсора/ошибку дальней страницы. POST/DELETE тест параметризован для task_file и project_file с проверкой маршрутов, If-Match и idempotency.

Live Corporate API, реальный PostgreSQL с данными заказчика, физический NAS/UNC, устройство другого сотрудника и ручной Narrator не проверялись. Недоступность устройства/сети/файла проверена детерминированными клиентскими fixtures и регрессиями существующего адаптера. Схема/сервер не менялись. Названия разрешаются отдельным GET на каждый связанный объект, последовательным обходом; batch API и новый кэш не создавались. В main этап не опубликован. Следующий функциональный этап можно выполнять на этой feature-ветке; интеграция в main и live приёмка остаются отдельными действиями.
