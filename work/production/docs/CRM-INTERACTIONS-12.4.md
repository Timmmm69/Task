# CRM 12.4 — взаимодействия и проверка задачи 12

Ветка: `feature/crm-contacts-workspace`. Изменения выполняются в её существующем worktree.

## Реализованный сценарий

В карточках корпоративного контакта и компании доступен общий компонент взаимодействий:
ограниченный просмотр, открытие серверной записи, создание с предзаполненным контрагентом,
редактирование темы, типа, даты, деталей, следующего шага и его срока, отмена формы.
Поддержан переход из глобального поиска/палитры через существующий маршрут CRM.
Следующий шаг не создаёт задачу, календарное событие или напоминание.

Использованы существующие GET/POST/PATCH `/api/v1/interactions` и GET контакта/компании.
Допустимые типы: `call`, `meeting`, `email`, `agreement`, `note`, `next_step`.
Тема: 1–500 символов после trim; детали: до 20000; следующий шаг: до 5000.
Пользователь вводит время с явным смещением, клиент отправляет UTC `Z`.
Редактирование остальных полей сохраняет исходную точность неизменённых дат.

Для чтения нужен `Contact.Read`, для создания `Interaction.Create`, для PATCH `Interaction.Update`.
Сервер выполняет object-level authorization взаимодействия и проверку связанных объектов.
Клиент повторно проверяет доступность/активность контрагента перед загрузкой и записью;
при открытии и после сохранения проверяет, что запись относится к текущему контрагенту.
PATCH не содержит `counterpartyObjectId` и `participantObjectIds`, использует исходные ID/version
и strong `If-Match`; ответ должен подтвердить более новую версию и правильную идентичность.
Конфликт оставляет ввод для сравнения и запрещает перезапись до перечитывания.

POST фиксирует payload и UUID idempotency key на время неопределённого результата.
Повтор отправляет те же данные с тем же ключом; форма при этом заблокирована для изменения.
Ошибки/исключения не превращаются в уведомление об успешной записи.
При смене scope/session удаляются чувствительные данные и отменяются запросы;
generation/token guards отсекают запоздалые ответы, включая навигацию по одному контрагенту.
Нет постоянного корпоративного кэша и очереди отложенных записей.

## Явные ограничения

- `PostgresProductApiQueries.List` разрешает `limit page cursor q lifecycle status parentId depth includeArchived sort`.
  Фильтра `counterpartyObjectId` нет; попытка использовать его отклоняется с 422.
  Компонент читает ровно одну страницу `limit=50` на действие пользователя и показывает только точные
  совпадения по ID текущего контрагента. Следующая страница заменяет предыдущую, а не накапливает их.
  Пустая страница означает отсутствие совпадений в этой странице, а не отсутствие истории.
  Даже при завершении обхода не обещается полная консистентная история: API не даёт snapshot этой выборки.
- Имена участников разрешаются только через подтверждённые GET доступных активных контактов и компаний
  из первых 20 связей. Скрытые объекты, остальные типы и оставшиеся связи не раскрываются;
  исходные UUID не показываются. Это ограничение клиента, а не максимальное число участников API (500).
- Создание в этом инкременте использует пустой список участников. Изменение участников, переназначение
  контрагента, удаление и восстановление взаимодействий не включены в этот редактор.
  Их endpoints существуют и отражены в SCR-117/PRD, но они не входят в основные AC-1–AC-7 задания 12.4.
  Они не объявляются реализованными или отсутствующими в API.
- Адреса контактов остаются GET/POST в рамках этапа 12.2. Новые операции с адресами не добавлены.

## Общая регрессия 12.1–12.4

Существующие тесты контактов, каналов/адресов и компаний сохранены и включены в общий gate.
Независимый review выявил пропущенные черновики каналов/адресов, подтверждения удаления канала
и компаний в `ModeSwitchGuard`. Они добавлены в существующий механизм Save/Discard/Cancel;
подтверждение удаления не трактуется как разрешение автоматического сохранения/удаления при смене режима.
В этот же механизм включены оба редактора взаимодействий и запрет смены режима во время записи.

Прямой GET контакта заменил обход до 500 страниц при корпоративной навигации из поиска.
Личный режим сохраняет собственный локальный адаптер и проверен отдельным тестом SQLite.
Независимый review также выявил необходимость защиты после вложенной навигации; regression test
проверяет, что более поздний переход к взаимодействию того же контрагента выигрывает.

В 12.4 не изменялись серверные API/DTO, БД, миграции и бизнес-требования.
В совокупной ветке этап 12.3 усилил проверку видимости контакта при удалении связи компании;
это изменение реализации авторизации без изменения публичного контракта.

## Воспроизводимая проверка

`work/crm_interactions_12_4/Run-Gate.ps1` создаёт изолированную PostgreSQL 16 на loopback/случайном порту,
проверяет Release solution, все три тестовых проекта и сохраняет TRX/логи/снимки WPF.
Используется короткий Windows-путь для совместимости PostgreSQL с кириллической рабочей директорией.
Кластер останавливается в finally; существующие службы и базы PostgreSQL не изменяются.
Результаты каждого фактического запуска, включая неуспешные и повторные, приведены в итоговом validation report.

Native WPF-тесты покрывают contact/company/interaction, создание, редактирование, конфликт,
binding errors и доступность кнопки сохранения при 800×600; большие состояния проверяются при 1100×1000.
Они используют синтетические клиенты, а серверные сценарии отдельно проверяются на реальной PostgreSQL.
Единый установленный клиент с live Corporate API, физический mixed-DPI и ручной Narrator acceptance
этими тестами не заменяются и не объявляются выполненными.
