# HAND-04 Руководство администратора Task

Версия: 1.0.0. Руководство предназначено для системного администратора организации. Оно дополняет, но не заменяет `OPS-operations-runbook.md`, `OPS-05-windows-client-release.md` и `backup-restore-runbook.md`. Текущий Windows-клиент не содержит отдельной графической консоли администрирования учётных записей: эти операции выполняются уполномоченным администратором через защищённый API или утверждённый корпоративный административный клиент.

## Границы ответственности

До выдачи доступа убедитесь, что сервер развёрнут по HAND-02, клиент получен из проверенного HAND-03 пакета и клиентское устройство доверяет корпоративной цепочке сертификатов. Для production обязателен корпоративный code-signing сертификат с RFC 3161 timestamp и контролируемый HTTPS origin. Внутренний self-signed сертификат release candidate подтверждает целостность стенда, но не является корпоративным издателем.

Не выполняйте administrative API из браузерной адресной строки, не передавайте пароли в тикетах и не используйте `http`, self-signed либо ошибочно выпущенные сертификаты как обход. При TLS-ошибке исправляйте DNS, SAN, цепочку доверия или срок сертификата по OPS-02/SEC-03.

## Роли и выдача прав

| Роль | Назначение |
| --- | --- |
| `system_administrator` | Учётные записи, роли, устройства, сессии и администрирование организации. |
| `system_manager` | Проекты, задачи, назначения и рабочие объекты в разрешённой области. |
| `system_employee` | Собственные и назначенные задачи, комментарии и доступные рабочие объекты. |
| `system_observer` | Только чтение доступных объектов. |

Новая учётная запись не получает бизнес-доступ автоматически. Назначайте минимально достаточную роль и проверяйте область объекта отдельно от роли. Явный deny, неактивная permission или отсутствие отношения к объекту закрывает доступ даже администратору там, где так требует политика. Нельзя удалить, деактивировать или заблокировать последнего активного администратора.

## Жизненный цикл учётной записи

Все маршруты ниже находятся под `/api/v1`. Tenant и исполнитель определяются по аутентифицированному запросу, а не из тела JSON.

1. Создайте пользователя: `POST /users` с правом `User.Create` и `Idempotency-Key`. Учётная запись создаётся в состоянии `pending activation`.
2. Установите временный пароль: `POST /auth/admin-reset-password` с `User.ResetPassword`, идентификатором пользователя, ожидаемой версией и `Idempotency-Key`. Генерируйте пароль в корпоративном менеджере секретов и передавайте его защищённым одноразовым каналом.
3. Активируйте запись: `POST /users/{id}/activate` с актуальными `If-Match`, `expectedVersion` и `Idempotency-Key`.
4. Назначьте роли: `PUT /users/{id}/roles` с `User.ManageRoles`, `organization.manage`, `If-Match` и `Idempotency-Key`.
5. Проверьте вход пользователя на синтетическом или целевом стенде. При первом входе временный пароль должен быть сменён до работы с бизнес-объектами.

Временный пароль действует 24 часа. Сброс пароля увеличивает credential version и отзывает все сессии и refresh tokens пользователя. Для изменения профиля применяйте `PATCH /users/{id}` с `User.Update`, `If-Match` и `Idempotency-Key`; не изменяйте состояние учётной записи через profile PATCH.

## Блокировка, сессии и устройства

При уходе сотрудника, утрате устройства или инциденте используйте одну из специальных операций, указав причину в restricted audit metadata:

- `POST /users/{id}/block` или `/deactivate` с `User.Block`, актуальными `If-Match`, `expectedVersion` и `Idempotency-Key`;
- `POST /users/{id}/unblock` или `/reactivate` для обратимого случая;
- `GET /auth/sessions` и `POST /auth/sessions/{id}/revoke` для сессий;
- `GET /devices`, `PATCH /devices/{id}` и `POST /devices/{id}/revoke` для устройств.

Block, deactivate и revoke отзывают связанные сессии и токены. Повторный revoke - no-op, но объект и права всё равно перепроверяются. Ошибки `OBJECT_NOT_VISIBLE`, `403`, `412` и `428` не обходите повторной отправкой: проверьте область, роль, текущую ETag-версию и заголовки. Конфликт версии означает, что нужно перечитать объект и повторить решение, а не перезаписывать изменения другого администратора.

## Установка, обновление и поддержка

1. Для новых ПК используйте подписанный `Install-TaskDesktop.ps1` из переданного release. Установщик проверяет издателя, манифест, SHA-256 и подписи до копирования файлов; ручная подмена файлов запрещена.
2. Для обновления публикуйте ZIP, `channel.json` и его подпись на контролируемом HTTPS origin. Не повышайте minimum client version, пока соответствующий подписанный пакет недоступен.
3. При неуспешной активации или pilot-приёмке используйте подписанный `Rollback-TaskDesktop.ps1`. Не редактируйте вручную `%LOCALAPPDATA%\Task` и не удаляйте кэш как «исправление».
4. При недоступности сервера пользовательские данные остаются read-only, а запись отключается. Проверяйте health, DNS, TLS и monitoring по HAND-02; не включайте offline-запись и не отключайте TLS-проверки.

Для backup, PITR, ротации сертификатов, мониторинга и incident cutover действуйте по operations runbook. Восстановление всегда сначала изолированное; production cutover требует процедуры и одобрения владельца инцидента.

## Подготовка обучения и demo

Используйте только изолированный профиль `qa03-deterministic-v1`. Он запускает реальный Release WPF, PostgreSQL и HTTPS API с ephemeral секретами, создаёт синтетические данные и удаляет стенд после проверки. Инструкция `HAND-04-demo-walkthrough.md` содержит роли, контрольные шаги и команду воспроизведения. Не направляйте demo-клиент на production, не импортируйте demo-сертификат в корпоративное хранилище и не используйте demo-пароли вне стенда.
