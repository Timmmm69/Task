# Employee Picker в проектах — 5.2 / 1.0.0

Реализовано в `feature/employee-picker` поверх сохранённого этапа 5.1 (`1cfb6c2`).
Исходная рабочая копия другой ветки с незакоммиченными изменениями не изменялась.
Эта задача относится к H: permissions, session lifetime и конкурентные операции; выполнена Codex.

## Поведение

- `CorporateApplicationContext` внедряет существующий `DesktopAdministrationApiClient` как
  `IDesktopEmployeeDirectory` в ProjectsViewModel. Оба места используют тот же
  `EmployeePickerView` / `EmployeePickerViewModel` этапа 5.1; второй picker не создан.
- Поиск, cursor, подтверждение учётной записи, login для однофамильцев и состояния ошибок остаются
  в общем компоненте. ViewModel хранит подтверждённый UserAccountId, а не строку поиска.
- Добавление сохраняет выбранную проектную роль, исходный project version, idempotency key и
  существующий AddMemberAsync. До отправки выполняется одиночная повторная проверка активности.
  Известное активное членство и неподтверждённый список участников блокируют команду.
- Успех обновляет version из authoritative response, затем перечитывает участников с сервера,
  сохраняя выбранный объект проекта. При неудачном перечитывании успех списка не объявляется.
- Руководитель необязателен: создание без руководителя, предзаполнение, смена и явное снятие
  назначения. Выбранный ID передаётся существующим DesktopProjectDraft. OwnerUserId не меняется.
  Неудачное предзаполнение не превращается в скрытое снятие руководителя; требуется новый выбор
  или явное «Без руководителя». Перед отправкой назначенного руководителя активность читается снова.
- Сохранён механизм If-Match и повторного сохранения после HTTP 412: версия перечитывается,
  черновик и выбранный руководитель сохраняются; автоматического повторного write нет.
- Имена разрешаются только для выбранного проекта и его участников, по уникальным ID, без обхода
  каталога страницами. Имя сопровождается login; недоступная запись — «Учётная запись · имя недоступно».
  Проектные роли используют прежний список, бизнес-правила назначения не меняются.
- Смена проекта освобождает прежний picker; generation/reference guards отклоняют запоздалый поиск,
  проверку сотрудника и разрешение имён. Запрос, ушедший на сервер до переключения, может завершиться
  там: UI нового проекта не получает его результаты; исходный проект нужно перечитать.
- Logout, деактивация поверхности, потеря capability и offline очищают directory data и выбор.
  Черновик проекта и хранимый ID руководителя сохраняются; после восстановления доступа требуется
  подтвердить руководителя снова. Записи автоматически не отправляются.
- 403 User API закрывает каталог и очищает имена, но не отменяет Project.ManageMembers для
  изменения роли/удаления участников. 403 Project API закрывает записи до нового набора capabilities.
  Terminal authentication failure закрывает session writes. 404, 412, state/validation failure и
  недоступный сервер не создают оптимистических участников или ложной версии.

## Матрица permissions

| Доступ | Добавление | Руководитель | Имена |
|---|---|---|---|
| Project.Read + Project.ManageMembers + User.Read | Общий picker | При Project.Create/Update — общий picker | Разрешённые GET users/{id} |
| Project.Read + Project.ManageMembers без User.Read | Существующий UUID-ввод | При Project.Create/Update — прежний необязательный UUID | Нейтральное отображение, 0 User API calls |
| Project.Read + User.Read без Project.ManageMembers | Команда закрыта, список участников не запрашивается | Только при Project.Create/Update | Владелец/руководитель через разрешённое чтение |
| Нет Project.Read / logout / offline | Запись закрыта | Запись закрыта | Новые directory reads запрещены |

Проверены `UserEndpoints`, `TaskPermissionAuthorization`, migration 012, bootstrap администратора,
Project store policies и `RequireActiveUser`. `user.read` — отдельное право, grant/deny копируются
из `identity.account.manage`; bootstrap system_administrator получает действующие permissions.
Имена ролей не заменяют effective permission. Наборы прав конкретной развёрнутой организации не
перечислялись: для обычного руководителя полнота зависит от фактических grants/denies.

Блокер остаётся: полный переход всех ролей на picker невозможен без отдельного утверждённого
решения по User.Read. Существующий работоспособный сценарий UUID сохранён. Новых прав,
серверных DTO, endpoints, БД/миграций, OpenAPI, календарной интеграции и передачи владения нет.

## Проверка

Результаты и receipts находятся в итоговом пакете
`outputs/20261015_project_employee_picker_5_2_1.0.0/validation-report.md`.
Используются fake API/HTTP fixtures и настоящие WPF-контролы в показанном Windows-окне.
WPF probe проверяет обе точки встраивания, реальную binding/command цепочку, видимость UUID,
доступность кнопки сохранения после прокрутки и fallback; сохраняет кадры обычной/узкой формы.
Это не live walkthrough production-аккаунтов и не ручной аудит screen reader.
Реальная PostgreSQL/сеть организации в этой задаче не использовалась; серверные write paths не менялись.

Готово для интеграции проектов с User.Read; общий этап 5.2 не означает снятие блокера полного role
coverage и не объявляет всё приложение готовым к deployment.
