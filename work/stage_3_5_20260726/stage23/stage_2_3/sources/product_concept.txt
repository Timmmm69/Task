# Концепция десктопного органайзера для компании

## 1. Общая концепция

Десктопный органайзер — внутренняя система компании для управления:

* задачами;
* расписанием;
* проектами;
* файлами и папками;
* контактами и контрагентами;
* совместной работой сотрудников.

Приложение устанавливается на рабочие компьютеры сотрудников и работает внутри локальной сети компании.

Данные о задачах, проектах, сотрудниках, контактах и структуре каталога хранятся централизованно на локальном сервере компании.

Сами рабочие файлы не загружаются в облако приложения. Они хранятся:

* на локальном сервере компании;
* на NAS;
* в общей сетевой папке;
* в отдельных случаях — на компьютере конкретного сотрудника.

Программа хранит ссылки на расположение файлов и связывает их с задачами, проектами и контактами.

Основная идея продукта:

> В одной системе пользователь связывает задачу, дату, проект, человека и необходимые для работы файлы.

---

# 2. Назначение продукта

Система предназначена для сотрудников одной компании.

Основные задачи продукта:

1. Централизовать рабочие задачи.
2. Сформировать единое расписание сотрудников.
3. Организовать проектную работу.
4. Упростить поиск рабочих файлов.
5. Связать документы с задачами и проектами.
6. Хранить информацию о контрагентах.
7. Обеспечить совместную работу внутри компании.
8. Снизить риск потери задач и договорённостей.
9. Обеспечить контроль выполнения работы.
10. Сохранить корпоративные данные внутри инфраструктуры компании.

---

# 3. Целевая модель использования

## 3.1. Одна компания

Система создаётся для одной конкретной компании.

В рамках системы существует:

* одна организация;
* один общий контур данных;
* несколько сотрудников;
* несколько отделов;
* личные и общие проекты;
* единая структура прав доступа.

Создание независимых компаний, публичная регистрация и SaaS-модель в первой версии не требуются.

## 3.2. Сотрудники

Каждый сотрудник получает отдельную учётную запись.

Использование одного общего логина несколькими людьми не допускается, поскольку в таком случае невозможно:

* определить автора изменений;
* корректно настроить права;
* вести историю действий;
* назначать исполнителей;
* контролировать ответственность.

## 3.3. Место работы

Основной сценарий — работа на компьютерах, подключённых к локальной сети компании.

Удалённое подключение может быть реализовано позднее через:

* корпоративный VPN;
* удалённый рабочий стол;
* защищённый доступ к локальному серверу.

# 4. Архитектура системы

## 4.1. Общая схема

На компьютеры сотрудников устанавливается десктопное приложение.

В локальной сети компании размещается центральный сервер.

```text
Компьютер сотрудника 1 ─┐
Компьютер сотрудника 2 ─┼── Локальная сеть ── Локальный сервер компании
Компьютер сотрудника 3 ─┘                         │
                                                 ├── База данных
                                                 ├── Сервер приложения
                                                 └── Общие сетевые папки
```

## 4.2. Десктопное приложение

На компьютере сотрудника выполняются:

* отображение интерфейса;
* создание и редактирование задач;
* календарь;
* локальные уведомления;
* открытие файлов;
* поиск;
* работа с проектами и контактами.

## 4.3. Локальный сервер

Локальный сервер используется для:

* хранения общей базы данных;
* синхронизации изменений между сотрудниками;
* управления пользователями;
* проверки прав доступа;
* хранения истории изменений;
* совместной работы;
* централизованного резервного копирования.

Локальным сервером может быть:

* отдельный сервер;
* мини-компьютер;
* выделенный офисный компьютер;
* NAS с поддержкой серверных приложений.

Предпочтительный вариант — отдельный мини-сервер или постоянно включённый компьютер.

## 4.4. Работа без внешнего облака

Для основной работы системе не требуется внешний облачный сервер.

Преимущества:

* отсутствует ежемесячная плата за хостинг;
* корпоративные данные не покидают инфраструктуру компании;
* высокая скорость работы внутри офиса;
* доступ к системе не зависит от внешнего интернета;
* большие файлы не передаются через интернет.

Ограничения:

* локальный сервер должен быть включён;
* компания самостоятельно отвечает за резервные копии;
* для работы вне офиса потребуется VPN или другой защищённый доступ;
* при отказе локального сервера общая работа временно останавливается.

# 7. Роли и права доступа

## 7.1. Администратор системы

Может:

* создавать сотрудников;
* блокировать учётные записи;
* назначать роли;
* управлять отделами;
* видеть все проекты;
* настраивать сервер;
* управлять резервными копиями;
* просматривать общий журнал действий.

## 7.2. Руководитель

Может:

* создавать проекты;
* назначать исполнителей;
* просматривать задачи сотрудников;
* контролировать сроки;
* редактировать задачи проекта;
* видеть историю изменений;
* работать с контактами и файлами проекта.

## 7.3. Сотрудник

Может:

* видеть назначенные ему задачи;
* создавать задачи в доступных проектах;
* изменять статус своих задач;
* прикреплять ссылки на файлы;
* оставлять комментарии;
* работать с доступными контактами.

## 7.4. Наблюдатель

Может:

* просматривать доступные проекты;
* просматривать задачи;
* просматривать файлы;
* просматривать комментарии.

Редактирование недоступно.

## 7.5. Гибкость прав

Права могут определяться:

* ролью пользователя;
* отделом;
* участием в проекте;
* ролью внутри конкретного проекта.

# 9. Раздел «Сегодня»

Раздел является главным рабочим экраном.

Он содержит:

* текущую дату;
* задачи на сегодня;
* почасовое расписание;
* задачи без точного времени;
* просроченные задачи;
* ближайшие напоминания;
* задачи на проверке;
* задачи, ожидающие действий других сотрудников.

## 9.1. Почасовое расписание

Задачи отображаются на временной шкале.

Для каждой задачи показываются:

* время начала;
* длительность;
* название;
* проект;
* приоритет;
* исполнитель;
* текущий статус.

Пользователь может:

* создать задачу кликом по времени;
* перетащить задачу;
* изменить время;
* изменить длительность;
* открыть карточку;
* завершить задачу;
* перенести её;
* отложить напоминание.

## 9.2. Задачи без времени

Задачи, имеющие дату, но не имеющие точного времени, отображаются отдельным списком.

Пользователь может перетащить задачу на временную шкалу.

## 9.3. Просроченные задачи

Просроченные задачи отображаются отдельным заметным блоком.

Доступные действия:

* открыть;
* завершить;
* перенести;
* изменить дедлайн;
* отменить;
* назначить другого исполнителя.

# 10. Раздел «Входящие»

# 14. Каталог файлов

## 14.1. Назначение

Каталог предназначен для систематизации файлов компании без загрузки их в облако приложения.

Система хранит:

* название;
* путь к файлу;
* расположение;
* тип файла;
* размер;
* описание;
* теги;
* связанные задачи;
* связанные проекты;
* связанные контакты;
* устройство или сетевой ресурс, на котором находится файл.

## 14.2. Древовидная структура

Пример:

```text
Каталог
├── Клиенты
│   ├── Компания А
│   │   ├── Договоры
│   │   ├── Акты
│   │   └── Переписка
│   └── Компания Б
├── Внутренние документы
├── Шаблоны
├── Финансы
└── Архив
```

Структура внутри программы может быть виртуальной и не обязана полностью повторять структуру папок Windows.

## 14.3. Типы элементов

В каталоге могут существовать:

* виртуальная папка;
* ссылка на локальный файл;
* ссылка на сетевой файл;
* ссылка на папку;
* интернет-ссылка;
* текстовая заметка.

## 14.4. Действия пользователя

Пользователь может:

* создавать папки;
* создавать разделы;
* переименовывать элементы;
* перетаскивать элементы;
* добавлять ссылки на файлы;
* добавлять ссылки на папки;
* добавлять теги;
* добавлять описание;
* связывать файл с задачей;
* связывать файл с проектом;
* связывать файл с контактом;
* открывать файл;
* открывать расположение файла;
* перемещать элемент внутри каталога;
* удалять и восстанавливать записи.

# 15. Хранение файлов

## 15.1. Основная модель

Программа не хранит содержимое файла.

Она хранит путь, например:

```text
\\COMPANY-SERVER\Documents\Clients\Alpha\Contract.docx
```

или:

```text
D:\Work\Clients\Alpha\Contract.docx
```

## 15.2. Рекомендуемое размещение

Общие рабочие файлы рекомендуется хранить:

* на файловом сервере;
* на NAS;
* в общей сетевой папке.

Это позволяет всем сотрудникам открывать один и тот же файл.

## 15.3. Локальные файлы

Если файл находится только на компьютере одного сотрудника:

* другие сотрудники видят запись о файле;
* система показывает, на каком устройстве он расположен;
* открыть файл с другого компьютера нельзя.

Пример статуса:

> Файл доступен только на компьютере «Бухгалтерия-01».

## 15.4. Проверка доступности

При открытии система проверяет:

* существует ли файл;
* доступен ли сетевой ресурс;
* имеет ли пользователь права;
* подключён ли нужный диск.

## 15.5. Если файл не найден

Система показывает:

> Файл не найден по сохранённому пути.

Доступные действия:

* указать новое расположение;
* открыть папку;
* найти файл вручную;
* удалить ссылку;
* оставить запись без активного файла.

## 15.6. Перемещение и переименование

Если файл перемещён через проводник Windows, старая ссылка может перестать работать.

В MVP пользователь вручную указывает новое расположение.

Автоматическое отслеживание перемещённых файлов по всему компьютеру в первую версию не входит.

## 15.7. Несколько путей

Для одного элемента каталога можно хранить несколько путей:

* сетевой путь;
* путь на офисном компьютере;
* путь на ноутбуке сотрудника.

Программа выбирает доступный путь для текущего устройства.

# 17. Уведомления

## 17.1. Типы

* приближение задачи;
* начало задачи;
* дедлайн;
* просрочка;
* назначение задачи;
* изменение исполнителя;
* комментарий;
* приглашение в проект;
* завершение задачи;
* задача отправлена на проверку.

## 17.2. Системные уведомления

Уведомления должны появляться поверх других окон операционной системы, если это разрешено настройками Windows.

Приложение должно иметь возможность работать в фоне.

## 17.3. Цветовая логика

Предварительная шкала:

* зелёный — до задачи больше 24 часов;
* жёлтый — от 6 до 24 часов;
* оранжевый — от 1 до 6 часов;
* красный — менее 1 часа;
* тёмно-красный — задача просрочена.

Пороговые значения должны настраиваться.

## 17.4. Действия из уведомления

* открыть задачу;
* завершить;
* отложить;
* перенести;
* закрыть.

## 17.5. Отсрочка

Варианты:

* 5 минут;
* 15 минут;
* 30 минут;
* 1 час;
* до завтра;
* выбрать дату и время.

## 17.6. Работа уведомлений

Уведомления запускаются самим десктопным приложением.

Для их работы внешний облачный сервер не требуется.

Если приложение закрыто полностью, уведомления могут не отображаться. Поэтому программа должна иметь фоновый режим и запускаться вместе с Windows.

---

# 18. Совместная работа

Сотрудники работают с одной общей базой через локальный сервер.

Изменения синхронизируются между компьютерами.

Примеры:

* руководитель назначил задачу;
* сотрудник увидел её у себя;
* сотрудник изменил статус;
* руководитель увидел обновление;
* сотрудник добавил комментарий;
* остальные участники получили уведомление.

## 18.1. Одновременное редактирование

Если два сотрудника одновременно изменяют одну задачу:

* сервер сохраняет последнюю подтверждённую версию;
* история фиксирует оба действия;
* при необходимости система предупреждает о конфликте.

Полноценное совместное редактирование одного текста в реальном времени в MVP не требуется.

---

# 19. Работа при отсутствии сервера

Если компьютер сотрудника временно потерял связь с локальным сервером:

* приложение показывает статус «Нет подключения»;
* ранее загруженные данные могут оставаться доступными для просмотра;
* локальные файлы продолжают открываться;
* сетевые файлы могут быть недоступны;
* изменения либо блокируются, либо временно сохраняются локально.

Для MVP допустим более простой вариант:

> При отсутствии сервера приложение работает в режиме просмотра без возможности изменять общие данные.

Полноценная офлайн-синхронизация может быть добавлена позднее.

# 22. Архив и корзина

## 22.2. Корзина

В корзину попадают удалённые:

* задачи;

* ссылки на файлы;
* виртуальные папки.

Удаление ссылки из программы не должно удалять сам файл с диска без отдельного явного подтверждения.

Это обязательное правило безопасности.

# 24. Авторизация

В первой версии не требуется публичная регистрация.

Учётные записи создаёт администратор компании.

Поддерживаются:

* вход по логину и паролю;
* сохранение сессии;
* выход;
* смена пароля;
* блокировка пользователя;
* принудительное завершение сессии.

Восстановление пароля может выполняться через администратора.

---

# 25. Безопасность

Необходимо:

* хранить пароли в виде безопасных хешей;
* проверять права на сервере;
* ограничивать доступ к проектам;
* вести историю действий;
* использовать защищённое подключение внутри сети;
* ограничивать доступ к базе данных;
* разделять права сотрудников;
* выполнять резервное копирование;
* защищать сервер паролем и firewall;
* не позволять приложению удалять физические файлы без отдельного подтверждения.

---

# 26. Резервное копирование

Компания должна регулярно копировать:

* базу данных;
* настройки сервера;
* общие сетевые папки;
* критически важные документы.

Рекомендуемая схема:

* ежедневная копия базы;
* еженедельная полная копия;
* хранение нескольких версий;
* одна копия на отдельном устройстве;
* периодическая проверка восстановления.

Резервная копия базы не заменяет резервное копирование самих файлов, поскольку программа хранит только ссылки.

# 29. Критерии готовности MVP

MVP считается готовым, если:

1. Администратор может создать сотрудника.
2. Сотрудник может войти в приложение.
3. Сотрудники видят общие данные через локальную сеть.
4. Руководитель может создать проект.
5. Руководитель может пригласить участников.
6. Руководитель может создать и назначить задачу.
7. Сотрудник видит назначенную задачу.
8. Сотрудник может изменить статус.
9. Изменение появляется у руководителя.
10. Задача отображается в календаре.
11. Пользователь получает всплывающее уведомление.
12. Пользователь может отложить или завершить задачу.
13. Пользователь может создать контакт.
14. Пользователь может связать контакт с задачей.
15. Пользователь может создать структуру каталога.
16. Пользователь может добавить ссылку на файл.
17. Файл открывается по сохранённому пути.
18. Сетевой файл открывается на другом компьютере.
19. При отсутствии файла система показывает ошибку.
20. Пользователь может изменить путь.
21. Все значимые изменения фиксируются в истории.
22. Удалённую запись можно восстановить из корзины.
23. Система показывает потерю соединения с сервером.
24. После восстановления соединения данные снова доступны.

# 30. Основные риски

## 30.1. Выход из строя локального сервера

Если сервер отключён или неисправен, общая работа прекращается.

Необходимы:

* стабильное питание;
* резервные копии;
* желательно источник бесперебойного питания;
* ответственный сотрудник.

## 30.2. Повреждение или удаление файлов

Программа не хранит сами файлы и не может восстановить их после удаления.

Компания должна отдельно резервировать сетевые папки.

## 30.3. Перемещение файлов

Если файл перемещён вручную, ссылка перестаёт работать.

В MVP путь исправляется вручную.

## 30.4. Неверные права доступа

Сотрудник может видеть ссылку, но не иметь прав Windows на открытие сетевого файла.

Права программы и права сетевой папки должны быть согласованы.

## 30.5. Удалённая работа

Без VPN сотрудники не смогут полноценно использовать систему вне офиса.

## 30.6. Слишком широкий продукт

Система объединяет таск-трекер, календарь, каталог документов и упрощённую CRM.

В первой версии необходимо ограничить каждый раздел базовыми сценариями.

# 31. Рекомендуемая техническая модель

Для одной компании рекомендуется:

* десктопное приложение для Windows;
* локальный backend;
* PostgreSQL;
* локальная сеть;
* отдельный мини-сервер или постоянно включённый компьютер;
* общая сетевая папка или NAS;
* хранение в базе только ссылок и метаданных файлов;
* ежедневные резервные копии;
* без внешнего облака;
* без Kubernetes;
* без микросервисов;
* без отдельного сервера для каждого модуля.

# 33. Главный сквозной сценарий

Для первой рабочей версии необходимо реализовать следующий сценарий:

1. Администратор создаёт сотрудника.
2. Сотрудник входит в десктопное приложение.
3. Руководитель создаёт проект.
4. Руководитель добавляет сотрудника в проект.
5. Руководитель создаёт задачу.
6. Указывает дату, время и дедлайн.
7. Назначает исполнителя.
8. Связывает задачу с контрагентом.
9. Добавляет ссылку на документ в общей сетевой папке.
10. Устанавливает напоминание.
11. Сотрудник видит задачу на своём компьютере.
12. Сотрудник открывает прикреплённый документ.
13. Сотрудник получает уведомление.
14. Сотрудник переводит задачу в работу.
15. Руководитель видит изменение.
16. Сотрудник завершает задачу.
17. Руководитель принимает результат.
18. Все действия сохраняются в истории.

Если этот сценарий работает стабильно на нескольких компьютерах внутри локальной сети, основа продукта считается реализованной.
