Концепция десктопного органайзера для компании
1. Общая концепция
Десктопный органайзер — внутренняя система компании для управления:
задачами;
расписанием;
проектами;
файлами и папками;
контактами и контрагентами;
совместной работой сотрудников.
Приложение устанавливается на рабочие компьютеры сотрудников и работает внутри локальной сети компании.
Данные о задачах, проектах, сотрудниках, контактах и структуре каталога хранятся централизованно на локальном сервере компании.
Сами рабочие файлы не загружаются в облако приложения. Они хранятся:
на локальном сервере компании;
на NAS;
в общей сетевой папке;
в отдельных случаях — на компьютере конкретного сотрудника.
Программа хранит ссылки на расположение файлов и связывает их с задачами, проектами и контактами.
Основная идея продукта:
В одной системе пользователь связывает задачу, дату, проект, человека и необходимые для работы файлы.

2. Назначение продукта
Система предназначена для сотрудников одной компании.
Основные задачи продукта:
Централизовать рабочие задачи.
Сформировать единое расписание сотрудников.
Организовать проектную работу.
Упростить поиск рабочих файлов.
Связать документы с задачами и проектами.
Хранить информацию о контрагентах.
Обеспечить совместную работу внутри компании.
Снизить риск потери задач и договорённостей.
Обеспечить контроль выполнения работы.
Сохранить корпоративные данные внутри инфраструктуры компании.

3. Целевая модель использования
3.1. Одна компания
Система создаётся для одной конкретной компании.
В рамках системы существует:
одна организация;
один общий контур данных;
несколько сотрудников;
несколько отделов;
личные и общие проекты;
единая структура прав доступа.
Создание независимых компаний, публичная регистрация и SaaS-модель в первой версии не требуются.
3.2. Сотрудники
Каждый сотрудник получает отдельную учётную запись.
Использование одного общего логина несколькими людьми не допускается, поскольку в таком случае невозможно:
определить автора изменений;
корректно настроить права;
вести историю действий;
назначать исполнителей;
контролировать ответственность.
3.3. Место работы
Основной сценарий — работа на компьютерах, подключённых к локальной сети компании.
Удалённое подключение может быть реализовано позднее через:
корпоративный VPN;
удалённый рабочий стол;
защищённый доступ к локальному серверу.

4. Архитектура системы
4.1. Общая схема
На компьютеры сотрудников устанавливается десктопное приложение.
В локальной сети компании размещается центральный сервер.
Компьютер сотрудника 1 ─┐
Компьютер сотрудника 2 ─┼── Локальная сеть ── Локальный сервер компании
Компьютер сотрудника 3 ─┘                         │
                                                 ├── База данных
                                                 ├── Сервер приложения
                                                 └── Общие сетевые папки
4.2. Десктопное приложение
На компьютере сотрудника выполняются:
отображение интерфейса;
создание и редактирование задач;
календарь;
локальные уведомления;
открытие файлов;
поиск;
работа с проектами и контактами.
4.3. Локальный сервер
Локальный сервер используется для:
хранения общей базы данных;
синхронизации изменений между сотрудниками;
управления пользователями;
проверки прав доступа;
хранения истории изменений;
совместной работы;
централизованного резервного копирования.
Локальным сервером может быть:
отдельный сервер;
мини-компьютер;
выделенный офисный компьютер;
NAS с поддержкой серверных приложений.
Предпочтительный вариант — отдельный мини-сервер или постоянно включённый компьютер.
4.4. Работа без внешнего облака
Для основной работы системе не требуется внешний облачный сервер.
Преимущества:
отсутствует ежемесячная плата за хостинг;
корпоративные данные не покидают инфраструктуру компании;
высокая скорость работы внутри офиса;
доступ к системе не зависит от внешнего интернета;
большие файлы не передаются через интернет.
Ограничения:
локальный сервер должен быть включён;
компания самостоятельно отвечает за резервные копии;
для работы вне офиса потребуется VPN или другой защищённый доступ;
при отказе локального сервера общая работа временно останавливается.

14. Каталог файлов
14.1. Назначение
Каталог предназначен для систематизации файлов компании без загрузки их в облако приложения.
Система хранит:

связанные контакты;

14.2. Древовидная структура
Пример:
Каталог
├── Клиенты
│   ├── Компания А
│   │   ├── Договоры
│   │   ├── Акты

│   └── Компания Б
├── Внутренние документы
├── Шаблоны
├── Финансы
└── Архив
Структура внутри программы может быть виртуальной и не обязана полностью повторять структуру папок Windows.
14.3. Типы элементов
В каталоге могут существовать:
виртуальная папка;

15. Хранение файлов
15.1. Основная модель
Программа не хранит содержимое файла.
Она хранит путь, например:
\\COMPANY-SERVER\Documents\Clients\Alpha\Contract.docx
или:
D:\Work\Clients\Alpha\Contract.docx
15.2. Рекомендуемое размещение
Общие рабочие файлы рекомендуется хранить:
на файловом сервере;
на NAS;
в общей сетевой папке.
Это позволяет всем сотрудникам открывать один и тот же файл.
15.3. Локальные файлы
Если файл находится только на компьютере одного сотрудника:
другие сотрудники видят запись о файле;
система показывает, на каком устройстве он расположен;
открыть файл с другого компьютера нельзя.
Пример статуса:
Файл доступен только на компьютере «Бухгалтерия-01».
15.4. Проверка доступности
При открытии система проверяет:
существует ли файл;
доступен ли сетевой ресурс;
имеет ли пользователь права;
подключён ли нужный диск.
15.5. Если файл не найден
Система показывает:
Файл не найден по сохранённому пути.
Доступные действия:
указать новое расположение;
открыть папку;
найти файл вручную;
удалить ссылку;
оставить запись без активного файла.
15.6. Перемещение и переименование
Если файл перемещён через проводник Windows, старая ссылка может перестать работать.
В MVP пользователь вручную указывает новое расположение.
Автоматическое отслеживание перемещённых файлов по всему компьютеру в первую версию не входит.
15.7. Несколько путей
Для одного элемента каталога можно хранить несколько путей:
сетевой путь;
путь на офисном компьютере;
путь на ноутбуке сотрудника.
Программа выбирает доступный путь для текущего устройства.

следующий шаг.
Интеграция с почтой и мессенджерами в MVP не требуется.

17. Уведомления
17.1. Типы
приближение задачи;
начало задачи;
дедлайн;
просрочка;
назначение задачи;
изменение исполнителя;
комментарий;

завершение задачи;

17.2. Системные уведомления
Уведомления должны появляться поверх других окон операционной системы, если это разрешено настройками Windows.
Приложение должно иметь возможность работать в фоне.
17.3. Цветовая логика
Предварительная шкала:
зелёный — до задачи больше 24 часов;
жёлтый — от 6 до 24 часов;
оранжевый — от 1 до 6 часов;
красный — менее 1 часа;
тёмно-красный — задача просрочена.
Пороговые значения должны настраиваться.
17.4. Действия из уведомления
открыть задачу;
завершить;
отложить;
перенести;
закрыть.
17.5. Отсрочка
Варианты:
5 минут;
15 минут;
30 минут;
1 час;
до завтра;
выбрать дату и время.
17.6. Работа уведомлений
Уведомления запускаются самим десктопным приложением.
Для их работы внешний облачный сервер не требуется.
Если приложение закрыто полностью, уведомления могут не отображаться. Поэтому программа должна иметь фоновый режим и запускаться вместе с Windows.

18. Совместная работа
Сотрудники работают с одной общей базой через локальный сервер.
Изменения синхронизируются между компьютерами.
Примеры:
руководитель назначил задачу;
сотрудник увидел её у себя;
сотрудник изменил статус;
руководитель увидел обновление;
сотрудник добавил комментарий;
остальные участники получили уведомление.
18.1. Одновременное редактирование
Если два сотрудника одновременно изменяют одну задачу:
сервер сохраняет последнюю подтверждённую версию;
история фиксирует оба действия;
при необходимости система предупреждает о конфликте.
Полноценное совместное редактирование одного текста в реальном времени в MVP не требуется.

19. Работа при отсутствии сервера
Если компьютер сотрудника временно потерял связь с локальным сервером:
приложение показывает статус «Нет подключения»;
ранее загруженные данные могут оставаться доступными для просмотра;
локальные файлы продолжают открываться;
сетевые файлы могут быть недоступны;
изменения либо блокируются, либо временно сохраняются локально.
Для MVP допустим более простой вариант:
При отсутствии сервера приложение работает в режиме просмотра без возможности изменять общие данные.
Полноценная офлайн-синхронизация может быть добавлена позднее.

22. Архив и корзина
22.1. Архив
В архив можно перемещать:
завершённые проекты;
старые задачи;
неактуальные контакты;
разделы каталога.
Архивные элементы сохраняются, но не отображаются среди активных.
22.2. Корзина
В корзину попадают удалённые:
задачи;
проекты;
контакты;
ссылки на файлы;
виртуальные папки.
Удаление ссылки из программы не должно удалять сам файл с диска без отдельного явного подтверждения.
Это обязательное правило безопасности.

24. Авторизация
В первой версии не требуется публичная регистрация.
Учётные записи создаёт администратор компании.
Поддерживаются:
вход по логину и паролю;
сохранение сессии;
выход;
смена пароля;
блокировка пользователя;
принудительное завершение сессии.
Восстановление пароля может выполняться через администратора.

25. Безопасность
Необходимо:
хранить пароли в виде безопасных хешей;
проверять права на сервере;
ограничивать доступ к проектам;
вести историю действий;
использовать защищённое подключение внутри сети;
ограничивать доступ к базе данных;
разделять права сотрудников;
выполнять резервное копирование;
защищать сервер паролем и firewall;
не позволять приложению удалять физические файлы без отдельного подтверждения.
